# ElimBar — Архитектура

Фандрайзинговая платформа ОБФ «Элим, барсыңбы?!» (Бишкек, КР). Один монолит
Laravel 12, два публичных контура (A — донор, B — фонд) на одной модели
данных, плюс третий контур (C — доверие), который не является приложением,
а есть свойство того, что A и B читают одни и те же таблицы.

Этот документ фиксирует форму системы. Правила по деньгам, RLS и платежам
не повторяются здесь подробно — они закреплены в коде (миграции,
констрейнты, триггеры, политики) и обязаны совпадать с этим описанием на
момент чтения. Если они разошлись — код и миграции старше и правы.

Статус: архитектурный каркас (миграции, модели, RLS, доменные контракты,
докер-компоуз, тесты на инварианты). UI контуров A и B, доменные сервисы
поверх моделей и реальный платёжный адаптер — предстоит реализовать поверх
этого каркаса.

## 1. Контуры

| Контур | Стек | Кто заходит | Что видит |
|---|---|---|---|
| A — Донор | Inertia + Vue 3 + Tailwind | Публика, доноры (OTP по телефону) | Витрина, кейс без ПДн, оплата, кабинет донора |
| B — Фонд | Filament | Оператор, верификатор, финансист, админ | Заявки, бенефициары, кейс-менеджмент, выплаты |
| C — Доверие | — (свойство БД) | — | Публичный отчёт = запрос к тем же таблицам, из которых работает бухгалтерия фонда |

Оба контура — один codebase, один `artisan`, один деплой. Разделение — на
уровне роутов, Eloquent-моделей/скоупов и **ролей PostgreSQL**, не на
уровне сервисов или отдельных приложений.

Донор и сотрудник фонда — разные сущности, не одна таблица `users` с
флагом роли: `App\Models\Donor` (вход по OTP, без пароля) и
`App\Models\User` (email/пароль, Filament, роли `spatie/laravel-permission`).
Смешивать их означало бы тащить в кабинет донора весь periметр
прав сотрудника — сознательно разделены с первой миграции.

## 2. Слои приложения

```
app/
  Domain/
    Payments/
      Contracts/PaymentGateway.php   единственная точка контакта с провайдером
      DTO/                            ChargeRequest, ChargeResult, PaymentIntent
      Adapters/NullPaymentGateway.php заглушка, пока провайдер не выбран (§6, §12)
      Services/WebhookGuard.php       идемпотентность вебхуков
    Donations/ · Cases/ · Beneficiaries/ · Subscriptions/ · Disbursements/
      Services/                       бизнес-логика домена (см. ниже)
  Models/
    Concerns/BelongsToTenant.php      Eloquent global scope + автозаполнение tenant_id
    Concerns/IsAppendOnly.php         defense-in-depth поверх БД-триггеров
    ...                               Donation, Allocation, Disbursement, FundCase, ...
  Support/TenantContext.php           единственный писатель app.tenant_id для сессии Postgres
  Providers/TenantServiceProvider.php вешает TenantContext на каждое новое подключение к БД
  Http/Middleware/SetTenantContext.php то же самое для HTTP-запроса
  Http/Controllers/                   контур A: тонкие, делегируют в Domain\*\Services
  Filament/                           контур B: Resources, Pages, Widgets (не бизнес-логика)
```

Бизнес-логика — только в `Domain/**/Services` (конвенция проекта:
контроллеры и Filament Resources её не содержат). Каждый денежный сервис
работает внутри `DB::transaction()` и не является единственной линией
защиты: инвариант обязан существовать как констрейнт/триггер в БД —
сервисный слой ему подчиняется, не заменяет.

## 3. Данные — ядро домена

```
Tenant
  └─ Beneficiary ──< CaseRequest ──> FundCase >── Campaign
                                        │
                        Donation >── Allocation ──< FundCase
                           │
                        Disbursement ──> Proof
```

Две модели названы не так, как таблицы, из-за зарезервированных слов PHP:
`FundCase` (таблица `cases`; `case` — часть синтаксиса enum с PHP 8.1) и
`CaseRequest` (таблица `requests`; `Request` уже занят
`Illuminate\Http\Request`).

- `Donation` — то, что дал донор. Append-only.
- `Allocation` — привязка (части) доната к конкретному кейсу. Append-only.
- `Disbursement` — то, что фонд реально выплатил по кейсу, с обязательным `Proof`. Append-only.
- Все денежные поля — `amount_minor bigint` (минорные единицы, тыйын) + `currency char(3)`. Никогда `float`.

Append-only на трёх уровнях, не один:
1. CHECK-констрейнт на знак суммы (`amount_minor > 0` для обычной записи,
   `< 0` для сторно через `reversal_of_id`).
2. Триггер `BEFORE UPDATE`/`BEFORE DELETE`, который бросает исключение на
   любую попытку изменить или удалить строку (`donations`, `allocations`,
   `disbursements`).
3. `App\Models\Concerns\IsAppendOnly` — та же защита на уровне Eloquent,
   срабатывает раньше похода в БД. Второй слой, не замена первому.

Инварианты — `allocated_minor <= amount_minor` (донат), `disbursed_minor <=
budget_minor` (кейс), `disbursement.proof_id NOT NULL`, запрет аллокации
закята на кейс с `allows_zakat = false` — реализованы как CHECK-констрейнты
и `BEFORE`/`AFTER`-триггеры прямо в миграциях, создающих таблицы
(`database/migrations/*_create_{allocations,disbursements}_table.php`).
Агрегаты (`cases.allocated_minor`, `cases.disbursed_minor`,
`donations.allocated_minor`) пишутся **только** триггерами; модель
`FundCase` бросает исключение при попытке присвоить их напрямую
(`FundCase::booted()`), чтобы ошибка проявлялась в PHP, а не только в logs
Postgres.

## 4. Мультитенантность

`tenant_id` есть во всех доменных и справочных таблицах с первого дня.
Два независимых слоя защиты:

1. **Eloquent global scope** (`BelongsToTenant`) — удобство и
   производительность, не бьёт индекс по `tenant_id` зря.
2. **PostgreSQL RLS-политика `tenant_isolation`** — граница безопасности.
   Читает `current_setting('app.tenant_id')`. Если Eloquent-скоуп забыт
   или обойдён сырым запросом, RLS всё равно не даст утечки между
   тенантами.

`app.tenant_id` для сессии Postgres проставляет `App\Support\TenantContext`
— не только в HTTP-запросе (`SetTenantContext` middleware), но и на **каждое
новое подключение к БД** через `TenantServiceProvider`, слушающий
`ConnectionEstablished`. Это осознанно: Horizon-воркеры и artisan-команды
живут дольше одного запроса и не проходят через HTTP middleware, но без
`app.tenant_id` RLS-политика молча вернёт ноль строк на любой запрос — это
не разовая настройка для контроллера, а свойство любого подключения к БД.

На фазе 1 существует единственный `tenant_id = 1`. Открытие для внешних
фондов в фазе 3 не требует смены модели данных — только резолвинг тенанта
по домену внутри `SetTenantContext` вместо константы из конфига.

## 5. Публичное/приватное разделение (контур доверия) и роли БД

Приложение никогда не подключается к Postgres владельцем схемы. Три роли:

| Роль БД | Кто использует | Что видит |
|---|---|---|
| `app_owner` (= `DB_USERNAME`) | миграции, деплой | всё — владелец таблиц |
| `app_staff` (= `DB_STAFF_USERNAME`, connection `pgsql_staff`) | контур B (Filament, домен, Horizon) | все домены своего `tenant_id`, включая `beneficiaries` и приватные колонки `cases` |
| `app_public` (= `DB_PUBLIC_USERNAME`, connection `pgsql_public`) | контур A (витрина, донат, автоотчёт) | **не имеет вообще никаких прав** на `beneficiaries` и на базовую таблицу `cases` — только `SELECT` на view `cases_public` |

`cases` физически разделяет публичные (`public_title`, `public_story`,
`public_photo_id`, агрегаты сумм) и приватные (`beneficiary_id`, всё, что
с ним связано) колонки. `app_public` читает кейсы только через
`cases_public` — `VIEW ... WITH (security_invoker = true)`, без приватных
колонок и без `beneficiaries`. `security_invoker = true` обязателен: без
него view выполняется правами владельца (обычно суперюзер миграций,
который по умолчанию `BYPASSRLS`), и RLS-политика `tenant_isolation`
на `cases` молча не применится к запросу через view.

Если контроллер контура A случайно потянет `->with('beneficiary')` —
Postgres вернёт `permission denied for table beneficiaries`, а не ФИО и
диагноз. Это не проверяется в контроллере — это невозможно физически.

Раскрытие конкретных данных бенефициара по явному согласию фиксируется в
`consents` (`beneficiary_id`, `document_version`, `granted_at`, `scope`) —
таблица версионированного согласия, не булево поле.

## 6. Платежи

`App\Domain\Payments\Contracts\PaymentGateway` — единственная точка
контакта домена с провайдером. Конкретный провайдер (открытый вопрос
фазы 0, см. §12) реализуется как адаптер за этим интерфейсом; домен не
знает про ELQR/эквайринг напрямую. До выбора провайдера
`AppServiceProvider` резолвит интерфейс в `NullPaymentGateway` — это держит
домен, вебхуки и тесты компилируемыми и тестируемыми уже сейчас.

Вебхуки идемпотентны через `payment_events`
(`UNIQUE(provider, external_event_id)`): `WebhookGuard::recordIfNew()`
сначала пытается вставить строку, обработка payload — только если вставка
реально произошла (ловит `23505` — unique violation — и возвращает `null`
на повторную доставку). Повторная доставка — ожидаемый сценарий, покрыт
тестом на каждый обработчик (`tests/Feature/Payments/WebhookIdempotencyTest.php`).

Рекуррент — не подписки провайдера (их обычно нет), а собственные
`subscriptions` + `subscription_charges`, управляемые джобами Horizon по
расписанию (`next_charge_at`), с лестницей ретраев 1/3/7 дней
(`retry_stage`) и паузой + письмом донору при исчерпании. Отмена подписки
— отдельный публичный эндпоинт без пароля, доступный по ссылке из
письма/кабинета (OTP при необходимости), не звонок в фонд. Механика
«ежедневная садака» (10 сом/день) работает на этой же инфраструктуре —
это не отдельная фича, а `frequency = 'daily'`.

## 7. Файлы

MinIO, приватный бакет (`config/filesystems.php`, disk `proofs`), доступ
только по подписанным URL с коротким TTL (`Proof::temporaryUrl()`).
`proofs` хранит `sha256`, исходное имя, mime, размер, кто загрузил —
публичного бакета для чеков расходов нет и не будет (ФИО и суммы).

## 8. Уведомления

Email/push/Telegram — чеки и напоминания. SMS зарезервирован только под
OTP-логин (стоимость: SMS в КР дороже самого доната в 10 сом/день).
Еженедельный дайджест по рекурренту вместо уведомления на каждое списание.

## 9. Локализация

`ky` и `ru` равноправны с первого релиза. Контент домена (заголовки,
описания кейсов, кампаний) — `jsonb` вида `{"ky": "...", "ru": "..."}`
прямо в таблицах (`cases.public_title`, `campaigns.title`, ...).
Интерфейсные строки — стандартный `lang/ky`, `lang/ru` Laravel.

## 10. Инфраструктура

Один `docker-compose.yml`, один VPS в КР (юрисдикция — включая бэкапы).
Без Cloudflare/внешнего TLS-терминатора до решения юриста по
трансграничной передаче (открытый вопрос #3). Caddy — TLS + reverse proxy
локально в периметре КР.

```
app       — php-fpm, Laravel (контуры A и B, один codebase)
horizon   — Horizon: очереди, ретраи подписок, обработка вебхуков, рассылки
scheduler — artisan schedule:run (лестница ретраев, ежедневная садака)
postgres  — PostgreSQL 16, RLS включён, роли app_owner / app_staff / app_public
redis     — очереди, кэш, сессии, Horizon
minio     — приватный бакет proofs (S3-совместимый)
caddy     — TLS-терминация, reverse proxy к app
```

## 11. Тесты и качество

- Pest, база — Postgres, не sqlite (`phpunit.xml`, `.env.testing`).
  Денежные инварианты живут в Postgres-триггерах/CHECK/RLS — тест на sqlite
  проверял бы только код, а не то, что действительно защищает деньги.
- Каждый денежный инвариант — пара тестов: happy path + попытка нарушить
  инвариант с ожиданием `QueryException` (см. `tests/Feature/Donations`,
  `tests/Feature/Disbursements`). Тест на happy path без парного теста на
  нарушение считается неполным (конвенция проекта).
- Каждый webhook-обработчик — тест на повторную доставку одного и того же
  `external_event_id` (`tests/Feature/Payments/WebhookIdempotencyTest.php`).
- Larastan уровень 6+ (`phpstan.neon`), обязателен в CI до мержа.

## 12. Открытые вопросы (блокируют часть работы)

1. **Платёжный провайдер не выбран.** Нужны коммерческие условия 2–3
   провайдеров с обязательной проверкой поддержки рекуррента. Домен уже
   абстрагирован через `PaymentGateway` — выбор не требует переписывать
   доменный слой, только новый адаптер.
2. **Юридическая конструкция доната.** Донат — целевое пожертвование
   фонду с указанием назначения, не перевод физлицу (зона НБКР). Оферта,
   чек и назначение платежа согласуются с юристом до запуска.
3. **Трансграничная передача.** Если перед сайтом ставится Cloudflare,
   TLS терминируется за пределами КР — нужна оценка юриста.
4. **Иностранное финансирование** — закон КР № 72 от 02.04.2024. Приём
   из-за рубежа отложен на фазу 2, мультивалютность уже в модели данных
   (`currency` на каждой денежной таблице).
5. **Синхронизация Бишкек — Ош** — механика обмена данными не выяснена.

Ни один из этих вопросов не блокирует модель данных — она уже учитывает
мультивалютность, типы фондов и RLS вне зависимости от ответа.
